# The E2E ladder

*Issue #150 (ring 1) · #278 (ring 1c) · #406 (rings 2–3) · #253 (ring 3b). Last updated
2026-08-01.*

Nightcore is a Rust/Tauri core over a Bun sidecar under a React board, and the
interesting failures live *between* those tiers. The ladder is the set of tests that
each cross one more boundary than the one below, so a regression is caught by the
cheapest tier that can see it.

The constraint that shapes the whole thing: **macOS's WKWebView exposes no CDP and no
WebDriver endpoint.** There is no way to drive the real app on the platform it is
primarily developed on. Every rung below is a consequence of working around that.

## The rungs

| Rung | Command | Crosses | Cost | Where it runs |
| --- | --- | --- | --- | --- |
| unit / integration | `bun run test:node`, `test:web`, `test:rust` | none | seconds | every PR (required) |
| **ring 1** | `cargo test` (`src/e2e/`) | subsystem composition, in-process `tauri::test` MockRuntime | seconds | every PR (required) |
| **ring 1c** | `cargo test` (`src/e2e/transcript_replay/`) | recorded provider output → the reader's correlation + finalizer seams | seconds | every PR (required) |
| **ring 3** | `bun run e2e:ring3` | **the sidecar process boundary** — real child, real NDJSON, real pipe, driven from TypeScript | **~1 s** | every PR (required, inside `ci.yml`'s bun job) |
| **ring 3b** | `bun run e2e:ring3b` (`cargo test`, `src/e2e/sidecar_boundary/`) | **the same pipe, driven from the CORE** — the real Rust `SidecarProvider` against the compiled sidecar, in a scratch git repo | **~1 s** | every PR (required, inside `ci.yml`'s `bun run test:rust`) |
| **ring 2** | `bun run e2e:ring2` | **the window + webview + IPC** — the real built app under WebDriver | ~5 min cold-cache **measured** (3m16s of it is the app build; the ring itself is **11 s**) | push to main · nightly · on demand · PRs labelled `e2e: ring2` |
| `dogfood:engine` | `bun run dogfood:engine` | a LIVE model | minutes + spend | manual only |
| `dogfood:gh` | `bun run dogfood:gh` | a real GitHub remote | minutes | manual only (`#[ignore]`d) |
| manual | `docs/testing/2026-07-11-manual-ui-dogfood-checklist.md` | a human | — | before a release |

## Why rings 3 and 3b are both needed

They cross the same OS pipe from opposite ends, and neither can see the other's half.

Ring 3 constructs its commands in TypeScript, from the same zod types the sidecar
validates with, so it is structurally incapable of catching a Rust-side serializer bug.
Ring 3b closes that: it drives `SidecarProvider::start_session` / `::query` — production
code with hand-written wire mapping (`parse_wire_enum`, the `Option` omissions, the
generated serde renames, the `requestId` injection) — and lets the live sidecar's zod be
the judge. **zod runs only in the sidecar**, so no Rust unit test and no codegen guard
can answer "does the core's payload validate?"; only a live child can. A rejected
command is silent on stdout, so the production symptom (a run that never starts) shows
up here as a wait that times out.

The inbound direction differs too. `contracts/fixtures.json` proves the *recorded*
shapes decode into `NightcoreEvent`; ring 3b proves the shapes the *running engine*
emits do — including `session-started` / `session-status`, which the supervisor
synthesizes and which appear in no transcript. And the `SurfaceQuery` → `query-result`
RPC (a `requestId`-correlated request/reply over an otherwise one-way protocol) has no
other ring at all.

Ring 3b runs against a scratch git repo in a temp dir with a temp `HOME` — never the
nightcore checkout — and its child is the compiled `binaries/nightcore-sidecar-<triple>`
that Tauri actually ships. `tauri_build` refuses to build the crate without that binary,
so it is present whenever the tests compile: the ring has no skip path, because a
skipped boundary proof reads exactly like a passing one.

## The one input: replay fixtures

`apps/desktop/src-tauri/src/e2e/transcript_replay/fixtures/*.jsonl` are NDJSON
transcripts — one serialized `NightcoreEvent` per line, in wire order — grounded
line-for-line in the codegen'd `contracts/fixtures.json`. There is exactly **one copy**,
consumed three ways:

- ring 1c's Rust drivers `include_str!` them,
- rings 3 and 3b point the sidecar's replay provider at the directory, so it reads them
  off disk and emits them through the provider seam,
- ring 2 sets the same provider behind the real app.

A second copy would drift silently, which is why the engine reads the Rust tree's files
rather than keeping its own.

## The fake provider

`packages/engine/src/providers/replay/` is a real `AgentProvider` whose model is a
transcript. It is registered **only** when `NIGHTCORE_E2E_REPLAY` names a readable
transcript directory, and when it is, it replaces the *whole* registry — the Rust core
threads a configured provider id down on every sidecar spawn, so leaving Claude
registered would serve it to any session that named one, which is exactly what a
zero-credential CI ring must never do. A set-but-unusable path **throws**: degrading to
a real provider would turn a job that believes it is offline into one quietly reaching
for a live account.

Select a transcript per run with a `#replay <name>` first line in the prompt; otherwise
the run replays `build`.

## Proving a ring is not vacuous

`bun run e2e:ring3 --prove` and the default ring-2 self-test both exist because a CI job
that can pass without exercising anything is worse than no job (this repo has found four
of those; see #422). Each perturbs the system and REQUIRES the battery to trip.

Ring 3 perturbs its fixture two ways — a payload field rewritten, an event line dropped
— and demands the battery trips on both.

Ring 3b carries its proof *inside* the ring rather than as a flag: one of its four tests
writes a raw, contract-violating `start-session` (one field out of the `TaskKind` enum)
and requires the live child to LOG a rejection and start no session. That is the premise
the other three rest on — the validator is live and rejecting — so their green means the
core's payload genuinely passed it, not that the sidecar accepts anything.

It was also verified by breaking the contract for real, once in each direction:

| break | applied to | result |
| --- | --- | --- |
| `requestId` written as `request_id` (the classic camelCase drift) | `provider/imp.rs::query` | ring 3b RED; **1586 other Rust tests still passed** — nothing else in the repo sees it |
| `session-completed` renamed on the wire | the sidecar's `encodeEvent` | ring 3b RED with the decode diagnosis naming the unknown variant and the offending line |

Ring 2 perturbs the live app once per check kind, and each perturbation must verify BY
EFFECT that it landed:

| kind | perturbation | proves |
| --- | --- | --- |
| `dom` | empty `#root`, blank the title | the DOM checks read rendered content |
| `ipc` | `create_task` over live IPC, mutating the real Rust store | `list_tasks` reads LIVE backend state, not a boot snapshot |
| `disk` | plant a quarantine file where the tripwire looks | the absence-assertion looks in the right directory |
| `session` | end the app | the two checks nothing narrower can falsify cannot be answered without a live app |

**Do not "fix" a red self-test by weakening it.** The first attempt monkey-patched the
page — `window.__TAURI_INTERNALS__.invoke = stub` and `delete __TAURI_INTERNALS__`. Both
fail: Tauri's IPC surface is non-configurable and non-writable by design, so the
assignment is silently discarded (WebDriver scripts run sloppy-mode) and the delete
throws `Attempting to change configurable attribute of unconfigurable property`. The
self-test correctly refused to certify the ring, and the answer was to break real state
instead of faking a break.

Two ring-2 checks admit no narrower perturbation, and this is stated rather than papered
over: `app_info` returns a version compiled into the binary, and the webview shim's
presence cannot be revoked from inside the page. They are proven against the app ceasing
to exist — a weaker claim (they cannot be answered without a live app, rather than that
they read the right field).

## Running ring 2 locally (Linux only)

```sh
sudo apt-get install -y webkit2gtk-driver xvfb
cargo install tauri-driver --version "^2" --locked
cd apps/desktop && bunx tauri build --debug --no-bundle && cd -
xvfb-run -a bun run e2e:ring2
```

On macOS this is not runnable at all — develop it through CI, which is why the script
dumps both the `tauri-driver` log and the app's own rolling log on any red.

## Known gaps (deliberate, not forgotten)

- **Ring 2 does not yet drive a task run through the UI.** It proves the shell over real
  IPC with real store data; the run pipeline is proven deterministically one rung down
  by ring 3. Driving a run adds verification/plan-gate semantics and a much larger flake
  surface to the ring that is hardest to iterate on. Worth doing next; not worth
  blocking rings 2–3 on.
- **No Windows rung.** WebView2 has a WebDriver story (`msedgedriver`), but nothing here
  is wired for it.
- **Ring 2 is not a required check yet.** The promotion criterion is written into
  `.github/workflows/e2e-ring2.yml`: 20 consecutive green runs with no re-run, and a
  warm-cache wall clock under 10 minutes.
